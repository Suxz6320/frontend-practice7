## 研究任务 1：OrbitControls 轨道控制器

### 引入方式

使用与案例复现相同的 CDN 版本（three 0.130.0），在 `three.min.js` **之后**
引入非 module 版 `examples/js/controls/OrbitControls.js`，它会把构造函数挂到
全局 `THREE.OrbitControls` 上（顺序不能反，OrbitControls 依赖 THREE 已存在）：

```html
<script src="https://cdn.jsdelivr.net/npm/three@0.130.0/build/three.min.js"></script>
<script src="https://cdn.jsdelivr.net/npm/three@0.130.0/examples/js/controls/OrbitControls.js"></script>
```

```js
const controls = new THREE.OrbitControls(camera, renderer.domElement);
```

### 关键配置（见 solar-system.js 第 3.1 节）

| 配置 | 取值 | 作用 |
| --- | --- | --- |
| `enableDamping` | `true` | 阻尼惯性，松手后相机缓缓停下，旋转更顺滑；**开启后必须每帧调用 `controls.update()`**，否则阻尼不生效 |
| `dampingFactor` | `0.06` | 阻尼系数，越小滑行越久 |
| `minDistance` | `3` | 滚轮最近距离，防止相机钻进太阳内部 |
| `maxDistance` | `40` | 滚轮最远距离，保证整个星系仍在视野内 |
| `enablePan` | `true` | 允许右键拖拽平移 |

默认鼠标映射：左键旋转（方位角/极角）、滚轮缩放（推拉相机距离）、右键平移。
极角默认不限，本场景允许从任意角度（包括轨道环下方）观察。

### 验证结果

浏览器实测：左键拖拽视角围绕太阳旋转，滚轮可拉近拉远且受 3/40 限制，
右键平移正常，松手有惯性，控制台无报错。
A-Frame 侧对应能力由内置的 `look-controls`（鼠标拖拽环顾）和
`wasd-controls`（键盘移动）提供，无需写 JS。

## 研究任务 2：点击交互（Raycaster 射线拾取）

### 从点击到命中的原理

浏览器只知道鼠标在二维屏幕上的位置，无法直接“点中”三维物体，Three.js 的
标准做法是射线检测（Raycasting），流程对应 solar-system.js 第 7.5 节：

1. **屏幕坐标转 NDC**：把像素坐标 `(clientX, clientY)` 换算成归一化设备坐标，
   x、y 都落在 -1 ~ 1（y 轴要取反，因为屏幕坐标向下为正）。
2. **发射射线**：`raycaster.setFromCamera(pointer, camera)` 从相机光心出发，
   穿过鼠标在近裁剪面上对应的那个点，得到一条三维射线。
3. **求交**：`intersectObjects(planets, true)` 让射线与物体的包围球、
   再与三角面求交；第二个参数 `true` 表示**递归检测子物体**，
   所以点中土星的光环、地球的月球也算命中。
4. **排序取最近**：返回的命中数组按距离从小到大排列，第一个就是最前面的物体。
   本场景中子物体（光环、月球）自身没有名字，因此沿 `parent` 向上回溯到
   行星本体，再读取 `userData.name / desc`。
5. **反馈**：选中行星给材质 `emissive` 赋蓝色并整体放大 1.15 倍
   （太阳用的是 MeshBasicMaterial，没有 emissive，只放大）；
   再用 `getWorldPosition + vector.project(camera)` 把行星世界坐标投影回
   屏幕坐标，让 HTML 信息标签每帧跟随行星；行星转到相机背后
   （NDC 的 z > 1）时隐藏标签。点击空白处取消选中并恢复原状。

工程细节：OrbitControls 也使用鼠标，为避免“拖拽转视角结束时误触选中”，
在 `pointerdown` 记录位置，`pointerup` 时位移超过 5 像素就判定为拖拽、不拾取。

### A-Frame 的对应方案

A-Frame 用相机下的 `<a-cursor raycaster="objects: .planet">` 组件完成同样的事：
cursor 内部也是一条 Three.js 射线，命中实体时浏览器化地派发 `click` 事件，
代码里给每个 `.planet` 实体 `addEventListener('click', ...)`，点击变亮黄、
再点恢复即可。声明式配置代替了手写射线。

### 验证结果

浏览器实测（执行结果摘录）：对地球屏幕坐标拾取得到 `directPick: "地球"`，
选中后 `emissive = 2e6bff`、`scale = 1.15`，标签显示
“地球：我们的家园，带着一颗卫星月球”；向画布派发 `pointerdown/pointerup`
真实事件同样触发选中；点空白处 `pickEmpty = null`，emissive 恢复 `000000`、
scale 恢复 1。A-Frame 版点击后颜色变为 `#ffe14d`、左上角信息更新，再点恢复。

## 研究任务 3：性能对比实验

实验页：`research/perf-test.html`，点“自动运行全部 6 组”即可复现。

### 实验方法与控制变量

- 每组都**新建 WebGLRenderer**，`setPixelRatio(1)` 统一像素比，排除高分屏干扰；
  组间 `dispose()` + `forceContextLoss()` 释放上下文与 GPU 资源。
- 场景为 N 个 0.8 边长立方体（**共享同一份几何体和材质**，隔离出的变量主要是
  draw call 数量与每帧矩阵更新），1 环境光 + 1 方向光、无阴影；
  所有立方体每帧自转，产生真实的逐物体 CPU 开销。
- 先预热 0.5 秒，再连续采样 120 帧，取平均 FPS 与平均单帧毫秒。
- A 组固定 1000 个物体，只切换 antialias；B 组固定 antialias 开，
  物体数取 100 / 1000 / 3000 / 5000。

### 实测数据（本机浏览器，2026-09-13）

| 组别 | antialias | 物体数量 | 平均 FPS | 单帧 ms |
| --- | --- | --- | --- | --- |
| A-1 | 关 | 1000 | 240.0 | 4.17 |
| A-2 | 开 | 1000 | 240.0 | 4.17 |
| B-1 | 开 | 100 | 239.9 | 4.17 |
| B-2 | 开 | 1000 | 240.0 | 4.17 |
| B-3 | 开 | 3000 | 176.3 | 5.67 |
| B-4 | 开 | 5000 | 129.2 | 7.74 |

### 结论

1. **抗锯齿组（A-1 vs A-2）**：1000 个物体时开关 AA 都是 240 FPS，
   差异小于 1%。原因是此规模下帧时间（约 4.2ms）远低于显示器刷新间隔，
   帧率被测试环境刷新率上限（约 240Hz）封顶，多出的 GPU 余量把 MSAA
   多重采样的填充率开销吸收掉了；肉眼差异体现在立方体边缘锯齿而非帧率。
   若在 60Hz 设备或更重场景（开阴影、高分屏、透明物体多）中，差距会更明显。
2. **物体数量组（B 组）**：100→1000 时帧率相同，说明低负载下瓶颈是刷新率上限，
   此时不能只看 FPS 判断开销（几组单帧 ms 实际都是 4.17）；
   物体升到 3000 时降到 176.3 FPS（5.67ms），5000 时降到 129.2 FPS（7.74ms），
   掉出刷新率上限后，draw call 提交与逐物体矩阵更新的线性增长开始主导帧时间。
3. **工程启示**：日常开发优先保持 antialias 开启（画面收益大、代价通常可接受）；
   物体数量才是主要风险，应优先用合并几何体
   （BufferGeometryUtils.merge）、实例化渲染（InstancedMesh）、
   降低球体/圆环分段数、减少光源与阴影来控制开销。
   主场景 `my-scene` 实际运行帧率约 240 FPS（右下角有实时 FPS 显示），
   星空使用单个 Points 对象（一次 draw call 画 2500 颗星）而非 2500 个球体，
   就是该结论的直接应用。

## 附：自主实践场景构成清单与两库选型理由

### Three.js 版（my-scene/）

- **几何体**：球体 SphereGeometry（太阳与六颗行星）、圆环体 TorusGeometry
  （土星光环）、环 RingGeometry（6 条轨道指示环）、点云 Points/BufferGeometry
  （2500 颗星空背景粒子），共 4 类不同对象。
- **材质**：太阳 MeshBasicMaterial（不受光，本身最亮）；行星 MeshStandardMaterial
  （roughness/metalness，受点光源照射产生昼夜面）；轨道环半透明 Basic；
  星星 PointsMaterial。
- **光源**：AmbientLight(0.25) 打底 + 太阳位置 PointLight(强度 2, 距离 100)。
- **相机**：PerspectiveCamera，fov 50，位置 (0, 6, 13) 俯瞰，远裁剪面 500。
- **动画**：Clock 按真实 delta 驱动；太阳自转、星空漂移；行星用
  “中心支点 Group + 行星挂 +x、每帧转 Group”的层级结构实现公转，
  行星本体自转，月球支点再嵌套在地球下实现绕地公转。
- **交互/适配**：OrbitControls 拖拽缩放平移；Raycaster 点击高亮 + HTML
  跟随标签；resize 时同时更新 aspect、投影矩阵、渲染器尺寸。

### A-Frame 版（my-scene-aframe.html）

同一主题的声明式实现：`a-sky` 深色天空、`a-sphere` 太阳与行星、
`a-ring` 轨道环、`a-torus` 土星光环、`a-light` 环境光与点光、
嵌套 `a-entity` + `animation`（linear 循环）实现公转/自转/月球，
`a-camera` 带初始位与 `a-cursor`，点击行星变色显示说明。
星空因 primitive 没有点云，注册了一个自定义 `starfield` 组件，
内部仍是 Three.js 的 Points。

### 选型理由

- 主场景选 **Three.js**：需要 Raycaster 拾取、选中高亮、HTML 标签的屏幕投影、
  点云、嵌套公转结构这类**精细、程序化的控制**，代码控制范式最直接。
- 同时补一个 **A-Frame** 版：同样的场景用标签十几分钟即可搭出，
  声明式 + 内置 animation/cursor/wasd/VR 支撑，适合快速原型与 WebXR 体验；
  但点云这类需求要自己写组件（内部还是 Three.js），印证了“要快速声明用
  A-Frame，要精细控制用 Three.js，复杂 A-Frame 项目最终仍需懂 Three.js”。
